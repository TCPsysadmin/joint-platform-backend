# Knowledge base

The source of truth for each workspace's content. It is split in two so that the
user's own filing system and the AI's organization never fight each other.

```
knowledge/workspaces/<workspace-slug>/
  library/     USER-OWNED. Any folders, any names. Users move and rename freely.
  wiki/        LLM-OWNED. Topic/entity pages the AI writes and rewrites.
  index.json   GENERATED by `python tools/kb/kb.py index`. Never hand-edit.
```

## How the two stay connected

Every library file has a stable `id` in its front matter. The wiki cites
sources **by id** (`[[src_20260930_k1ck0f]]` plus a `sources:` list), never by
path. `index.json` maps each id to wherever the file lives right now, so a user
reorganizing `library/` never breaks the wiki, and the AI never has to touch
the user's folders.

## Library file format

```markdown
---
id: src_20260930_k1ck0f        # from `python tools/kb/kb.py new-id`; never changes
type: transcript               # transcript | summary | document | note
title: Kickoff call
media: b2://<bucket>/<key>     # optional; video/audio stay in B2, never in git
summary_of: src_...            # summaries only: the transcript they summarize
tags: [onboarding]
---
text...
```

## Wiki file format

```markdown
---
title: Onboarding
sources: [src_20260930_k1ck0f, src_20260930_brand1]
---
Prose with inline citations [[src_20260930_k1ck0f]].
```

`wiki/index.md` is the entry page and `wiki/log.md` records each change the AI
makes. See [AGENTS.md](AGENTS.md) for the rules the AI follows.

## Checks

`python tools/kb/kb.py check` (also run in CI) fails when:
- a library file has no id, a malformed id, or a duplicate id
- a wiki page cites an id that is not in the library
- a summary's `summary_of` points nowhere
- `index.json` is out of date

## Search

Supabase (pgvector) remains the search index, but it is **derived** from this
folder: re-embed changed library files on push. If Supabase is ever wiped it can
be rebuilt from git.

## Things to decide before real client data lands here

- **Access control is per repo, not per folder.** Anyone with access to this repo
  can read every workspace. Client data probably belongs in a separate data repo
  (or one per client) rather than next to the code.
- **Deletion means history rewrite.** Git keeps every version; honoring a
  "delete my data" request requires rewriting history on every clone.
- **Size.** GitHub rejects files over 100 MB and warns past a few GB per repo.
  Only text and pointers go in git; media stays in B2.
